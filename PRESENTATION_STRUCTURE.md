## Слайд 5: Реализация RAG Platform
**Заголовок:** RAG Platform - Техническая реализация

**Проблема:**
Как интегрировать статичную базу знаний в динамические AI-взаимодействия?

**Решение:**
Реализован RAG (Retrieval-Augmented Generation) с векторным поиском

**Архитектура RAG:**

1. **Индексация (при запуске):**
   - Чтение документов из `database.xlsx`
   - Генерация embeddings через OpenRouter API
   - Сохранение в in-memory векторное хранилище
   - Время: ~100-200 сек на 100 документов

2. **Поиск (при запросе):**
   - Конвертация запроса в embedding (1536 измерений)
   - Поиск Top-K документов по косинусному сходству
   - Возврат релевантных документов с оценками
   - Время: <1000ms

**Технические детали:**
```go
// Пример: Генерация embedding
embedding, err := embeddingClient.GetEmbedding(text)

// Пример: Поиск по векторному хранилищу
documents, scores, err := vectorStore.Search(queryEmbedding, topK)
```

**Интеграция с Orchestrator:**
- Orchestrator вызывает RAG Platform через gRPC
- Полученные документы вставляются в промпт LLM
- LLM генерирует ответ с учетом знаний из базы

**Визуал:** Диаграмма потока данных RAG + код примеры

## Слайд 6: ADK Framework и оркестрация агентов
**Заголовок:** ADK Framework - Упрощение разработки агентов

**Проблема:**
Разработка каждого агента требует реализации:
- gRPC сервера
- Управления задачами
- Интеграции с LLM
- Хранения истории
- Обработки ошибок

**Решение:**
Создан ADK (Agent Development Kit) - библиотека, абстрагирующая общую логику

**Что предоставляет ADK:**
- ✅ Готовый gRPC сервер с A2A протоколом
- ✅ Абстракция LLM провайдеров (Eliza, OpenRouter)
- ✅ Автоматическое управление жизненным циклом задач
- ✅ Интеграция с MongoDB для истории
- ✅ Поддержка специализированных агентов
- ✅ Асинхронное выполнение задач

**Пример использования:**
```go
// Создание сервера
server, _ := adk.NewServer(adk.ServerConfig{
    Port:               ":50051",
    Provider:           provider,
    SendMessageHandler: methods.SendMessage,
    GetTaskHandler:     methods.GetTask,
})

// Регистрация специализированного агента
server.RegisterNewAgent(agents.Agent{
    Name:        "weather-agent",
    Description: "Weather information agent",
    Url:         "localhost:50056",
})
```

**Результат:**
Создание нового агента сократилось с ~1000 строк до ~50 строк кода

**Визуал:** Сравнение кода "до" и "после" использования ADK

## Слайд 7: Специализированные агенты и маршрутизация
**Заголовок:** Система специализированных агентов

**Реализованные агенты:**
1. **Authors Agent** (порт 50052) - информация об авторах проекта
2. **Crypto Agent** (порт 50053) - данные о криптовалютах
3. **Football Agent** (порт 50054) - спортивная информация
4. **News Agent** (порт 50055) - агрегация новостей
5. **Weather Agent** (порт 50056) - информация о погоде

**Механизм маршрутизации:**
1. Orchestrator получает запрос пользователя
2. LLM анализирует запрос и доступные агенты
3. LLM решает, нужен ли вызов специализированного агента
4. Если да - Orchestrator вызывает агента через gRPC
5. Ответ агента добавляется в контекст разговора
6. LLM формирует финальный ответ с учетом информации от агента

**Протокол Agent-to-Agent:**
- Стандартизированный gRPC интерфейс
- Все агенты реализуют одинаковый A2A протокол

**Визуал:** Диаграмма взаимодействия агентов

## Слайд 8: Асинхронная обработка и управление задачами
**Заголовок:** Асинхронная обработка задач

**Проблема:**
LLM запросы могут занимать несколько секунд. Блокирующая обработка недопустима.

**Решение:**
Реализована асинхронная модель с отсоединенными задачами (detached tasks)

**Жизненный цикл задачи:**

```
1. SendMessage → Создание задачи (TASK_STATE_PENDING)
   ↓
2. Сохранение начального состояния в MongoDB
   ↓
3. Запуск goroutine для обработки
   ↓
4. Получение истории разговора
   ↓
5. Вызов RAG Platform (если нужно)
   ↓
6. Обработка LLM провайдером
   ↓
7. Вызов специализированных агентов (если нужно)
   ↓
8. Сохранение результата (TASK_STATE_COMPLETED)
```

**Технические детали:**
- Использование `context.Background()` для отсоединенных задач
- Автоматическое управление состоянием в MongoDB
- Polling через `GetTask` для получения результатов
- Обработка ошибок с сохранением статуса `TASK_STATE_FAILED`

**Преимущества:**
- Неблокирующая обработка запросов
- Возможность обработки тысяч запросов одновременно
- Сохранение состояния при сбоях

**Визуал:** Диаграмма состояния задачи + временная шкала

## Вопросы, которые могут задать:

**Q: Почему Go, а не Python?**
A: Go обеспечивает лучшую конкурентность для асинхронной обработки, компилируется в один бинарник, проще развертывание.

**Q: Зачем нужен ADK, если можно было использовать готовые фреймворки?**
A: ADK специфичен для нашей задачи, обеспечивает единообразие всех агентов, упрощает разработку.

**Q: Как обеспечивается отказоустойчивость?**
A: Каждый сервис независим, ошибки обрабатываются и сохраняются в MongoDB, можно добавить retry логику.
